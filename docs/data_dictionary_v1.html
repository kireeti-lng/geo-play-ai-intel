Build notes · data_dictionary.py · Version 1

A typed schema, turned into a described dictionary.

The GeoPlay deliverable: a JSON schema export — tables, columns, and their SQL data types — becomes a per-column data dictionary with a business description and a confidence rating on every row. This is exactly what the script does and the reasoning behind each design choice — no more, no less than what the code runs.

script data_dictionary.py input schema.json (typed) batch size 10 tables temperature 0.1 model openai/gpt-5.6-luna outputs JSON + CSV status DRAFT — descriptions need review
01

What it does

One input file, two output files, one API loop in between.

The input is a JSON schema at payload_source/schema.json — a list of tables, each carrying its columns and each column's SQL data_type. Because the export is already structured by table, the script does no grouping of its own: it loads the file, batches the tables, and asks the model to describe each column in the context of its table and its type. The output is a data dictionary with one row per table + column, each carrying a business description and a confidence rating.

The one big change from the earlier CSV version: the model no longer works from a bare name. Each column now arrives as column_name (DATA_TYPE), so a TIMESTAMP is described as a point in time, a BOOL as a status flag, and a NUMERIC as a metric — the type is a fact fed in, not a guess.

Principle

Give the model the context the source already has. Table grouping and SQL types were sitting in the schema export — passing them through costs almost nothing and sharpens every description.

04

Design decisions, and the reasoning

Four choices baked into the script. Each had a plausible alternative.

Why 10 tables per request

The batch size sets three things at once. One table per request would mean as many calls as there are tables: slow, and a fresh chance to fail on each. Every table in one request would be a single call, but the reply would be enormous and far more likely to be truncated — and truncated JSON is unparseable, so a single overrun loses the whole response.

Ten lands in the middle, and it dropped from twenty in the earlier version for a reason: now that every column carries its data type and a fuller, two-sentence description comes back, each table's share of the reply is larger. A smaller batch keeps each JSON object comfortably within reach and the blast radius small if one batch fails.

Rule of thumb

Pick the batch size from your output budget, not your input. Input is cheap and rarely the constraint; the reply is what gets truncated, and with structured JSON a truncation isn't a partial result — it's an unusable one.

Why feed the data type with every column

A bare name is ambiguous; a name plus its type is nearly resolved. Sent as ended_at (TIMESTAMP) the model knows it is a point in time; is_payer (BOOL) is clearly a status flag; arpdau (NUMERIC) is a metric. The prompt makes this explicit with a "Respect Data Types" rule, so the type shapes precision and semantics rather than being ignored.

The type was already sitting in the schema export — passing it through costs a few input tokens per column and measurably sharpens the output. Input tokens are the cheap half of the bill, so this is close to free.

Why pin the temperature to 0.1

A data dictionary is reference material, not creative writing. temperature=0.1 pushes the model toward its most likely, most factual phrasing and away from stylistic variation — so re-running the same schema tends to produce the same descriptions, and the output reads as documentation rather than improvisation.

It pairs with the anti-tautology rule: low temperature keeps the wording stable, and the rule keeps it from settling on the laziest stable answer — restating the column name.

Why re-clean the model's rows before saving

Even in JSON mode the model can echo back extra keys — most obviously the data_type it was shown. Rather than trust the reply's shape, the script rebuilds each row from scratch with exactly four keys (table_name, column_name, confidence, description) and defaults a missing confidence to high. The output schema is enforced by the code, not requested from the model.

The cleaned rows are accumulated and written once at the end — JSON with a metadata envelope (domain, source_file, total_tables, total_columns) for programs, and CSV for analysts, the utf-8-sig BOM keeping accented text readable in Excel.

05

The output shape

Four fields per row, wrapped in a small envelope.

output/data_dictionary.json — envelope + one entry per table column
{
  "domain":         "GeoPlay Agentic AI Mobile Gaming Analytics",
  "source_file":    "payload_source\schema.json",
  "total_tables":   <count of tables in the schema>,
  "total_columns":  <count of rows described>,
  "columns": [
    {
      "table_name":   "dim_ab_variant",
      "column_name":  "variant_id",
      "confidence":   "high",
      "description":  "Unique identifier of an A/B test variant..."
    }
  ]
}

Each entry carries exactly four fields — table_name, column_name, confidence (one of high, medium, low), and description. The data_type the model was shown is deliberately not carried into the output — it's an input signal, cleaned back out so the dictionary stays about meaning, not storage. Around the list sits an envelope with the domain, the source path, and table and column totals, so the file documents its own provenance even after it drifts away from the conversation that produced it.

The CSV holds the same four fields, one row per table column, ordered table_name, column_name, confidence, description — the same data, shaped for a spreadsheet.

06

What this output is, and isn't

The honest boundary around the deliverable.

Every description here is inferred from a name, its table, and its SQL type. That's more than the earlier CSV version had — the type genuinely narrows the guesswork — but the schema still carries no sample values, no nullability, no row counts, and no existing documentation. The model never touched the warehouse; it read a schema export and reasoned from it.

The failure mode that matters isn't a wrong answer, it's a confident-sounding wrong answer. A dictionary entry that reads authoritatively but is invented is worse than a blank one, because nobody goes back to check it. This is why the confidence field exists on every row: sort by it and read the low and medium rows first. Treat it as triage, not proof — a high is where to look last, not a guarantee.

Fit for

  • ✓A first draft that turns a typed schema into readable documentation
  • ✓Onboarding context — an approximate map beats no map
  • ✓Finding naming inconsistencies across every table in the schema
  • ✓A starting point analysts correct rather than author from scratch

Not fit for

  • ✗Publishing as authoritative documentation unreviewed
  • ✗Compliance or governance artifacts needing verified lineage
  • ✗Asserting units, allowed values, or exact semantics — the type hints at these but sample data would confirm them
  • ✗Deciding whether two same-named columns really hold the same thing

One structural note on repeated columns: because the script describes each table independently, a column that appears in several tables gets a separate row — and separate wording — each time. That safely preserves cases where platform means the OS in one table and the ad platform in another. The flip side is there's no consistency pass: two rows for a column that really does mean the same thing may come back phrased slightly differently, though the low temperature keeps that drift small.

07

What V2 should change

Ordered by how much accuracy or safety each buys per unit of effort.

1

Add sample values and nullability

Data types are now fed in — the next accuracy lever is showing the model what the columns actually hold.

  • Add 3–5 distinct sample values per column where you can. status (STRING) is still a guess; status with values A / C / X is nearly solved.
  • Include is_nullable from INFORMATION_SCHEMA.COLUMNS, so an optional flag reads differently from a required key.
  • Extend the prompt's "Respect Data Types" rule to "respect the values too" once they're present.
Success looks likeThe share of rows tagged low and medium confidence drops sharply.
sample valuesis_nullable
2

Save incrementally for crash resilience

Right now the outputs are written once, at the end — a failure on the last batch discards every earlier one.

  • Write the JSON after each batch returns, so a crash keeps the batches already completed on disk.
  • On startup, load whatever is already there and resume from the first table not yet described.
Success looks likeA failure partway through costs the current batch, not the whole run.
3

Pull the schema straight from the warehouse

Right now the script reads a hand-exported schema.json — the source of truth is a step removed.

  • Query INFORMATION_SCHEMA.COLUMNS directly and build the same {tables:[...]} shape in code, so there's no manual export to keep fresh.
  • Validate the loaded schema up front — every table has a name, every column a data_type — and fail loudly on a malformed file.
Success looks likeRunning the script always reflects the live schema, with no stale intermediate file.
4

Add a consistency pass

Because each table is described on its own, a column repeated across tables can come back worded differently. Make the wording uniform.

  • Group repeated column names and check the phrasing is parallel where the meaning is the same.
  • Build a small glossary of recurring terms and feed it into the prompt so vocabulary stays stable across batches.
Success looks likeThe same column reads the same way wherever it appears — one voice, not one per batch.
5

Make re-runs cheap

Only pay for what changed when the warehouse evolves.

  • Load the existing output on startup and skip table columns already described.
  • Add a flag to force a refresh of just the low-confidence rows after you've improved the input.
Success looks likeAdding one table costs one small batch, not a full re-run.
