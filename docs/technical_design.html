Technical design document

Natural language to trustworthy SQL, over a governed games warehouse

A metadata-driven NL-to-SQL pipeline. It describes a 50-table BigQuery warehouse, defines 49 business metrics, and feeds both to a language model together with a rule set and a deterministic validator, so the SQL it writes uses real columns and computes each metric with the denominator its definition specifies.

repo geo-play-ai-intel python 3.12.4 model openai/gpt-5.2 · OpenRouter modules 5 geoplay + 7 scripts warehouse BigQuery · 50 tables · 948 columns
01

Business case

Why a metadata layer exists between the question and the query.

Game teams ask analytics questions in words — "what is ARPU for the last 30 days", "D7 retention by country" — and wait on an analyst to write SQL. The obvious shortcut is to hand the question to a language model. Done naively that fails in two ways, and both fail silently: the model invents table and column names, and it guesses metric formulas. The query runs, returns a number, and the number is wrong. Nobody can tell by looking at the output.

This project removes both guesses before generation, then verifies the result after it.

948

49

The core idea

A data dictionary tells the model what exists. A metric catalogue tells it what things mean — that ARPU divides by all active users while ARPPU divides by payers only. A rule set tells it how to build a query safely. A validator then checks what it actually wrote. Schema alone carries none of the last three.

Who this serves

ConsumerNeedWhat the pipeline gives them
Game / product teamsAn answer without waiting on an analystReadable SQL they can hand to a runner
AnalystsA first draft that respects metric definitionsDenominators already pinned to the catalogue
Data platformQueries that do not blend tenants or scan whole tablesTenant grouping and partition-pruning rules, enforced by checks
The production NL-to-SQL agentA place to test prompt and rule changesA local twin sharing the production class and interface

Evidence it works

Asked for ARPDAU over seven days, the model wrapped a per-day aggregate in an outer AVG() — the arithmetic mean of daily values, exactly as the catalogue definition prescribes, and not the naive reading a bare schema suggests. Asked for D7 retention, it excluded cohorts younger than seven days. Neither behaviour was in the question; both came from the definitions.

02

Architecture

Three build stages produce metadata; one generation stage consumes it; a validator closes the loop.

Two generation paths, one rule set

There are deliberately two generators. sql_generation_simple.py makes one direct chat call. sql_generation.py is a copy of the production LangChain agent and reaches its context through a tool call. Both import the same geoplay/rules.py and the same geoplay/validate.py, so a rule or check change lands on both at once.

how the shared rules reach each generator
rules.py ── build_rules() ─────────────────► sql_generation_simple.py   (system prompt)
         │
         └► tools.py ── build_rules() + build_context() + build_reminder()
                                     └─────► sql_generation.py          (tool response)
A positional gotcha

The agent receives the rules inside a tool response followed by ~109,000 characters of schema, so by the time it finishes reading the table list the rules are 109k characters behind it. That measurably changed which tables it chose. build_reminder() exists for exactly this: 666 characters restating the load-bearing rules, appended after the schema so they are the last thing read.

04

geoplay/config.py

One job: hand back a configured chat model. 31 lines.

What it achieves. It is the single place that knows how to reach the LLM provider. Nothing else in the agent path constructs a client, so the model, the endpoint and the temperature are changed in one file.

Where it is used. sql_generation.py calls get_llm() in its constructor, and LangChain's create_agent takes the result as its model. The simple script never touches it — it builds a plain OpenAI client inline instead, which is what keeps it free of the LangChain dependency tree.

Why it exists at all. It mirrors the production geoplay.config module path exactly, so the import line in the production agent file needed no edit. That fidelity is the point: a change reviewed here is a copy-paste into production.

FunctionReturnsBehaviour
get_llm(model_name=None)ChatOpenAIResolves the model from the argument, then OPENROUTER_MODEL, then DEFAULT_MODEL. Points at the OpenRouter base URL with temperature=0.1.
Deliberate omission

Production's get_llm also attaches a token-metering callback from geoplay.tokens. That is internal to the other repository and is left out here. Everything else — the base URL, the temperature, the model fallback chain — matches.

05

geoplay/rules.py

The behavioural contract for every generated query. 219 lines, 10 sections, ~7,900 characters of prompt text.

What it achieves. It converts hard-won corrections into standing instructions. Every rule in it exists because a real generated query got something wrong — a wrong denominator, an invented date range, a guessed string literal, a full table scan. It is the accumulated memory of those failures.

Where it is used. Both generators. The simple script embeds build_rules() in its system prompt; the agent gets it through tools.py. Sharing one module is what stops the two drifting apart — an early version of this project had separate prompts, and a rule added to one silently did not apply to the other.

Why pure standard library. It imports only os and dotenv. If it imported anything from LangChain, the simple script would inherit ~30 transitive packages it does not need.

SectionGoverns
APPROACHThe method: settle the question, read the definition, find columns that already hold the inputs, judge on correct / simple / effective, re-read the question before returning
CHOOSING THE TABLEOne table where possible; purpose-built tables; business-named columns over a generic metric_id shape
OUTPUT SHAPEFinal SELECT aligns exactly with the request; window columns for period aggregates and none for time series; one row per named period
TIME RANGENever invent a range; resolve partial dates; require every named month present; range predicates on raw date columns
AGGREGATION SAFETYNever SUM ratios or daily distinct counts; compute period ratios at daily grain; never approximate one metric from another
COUNTING AND JOINSFan-out protection; COUNT(DISTINCT …) over COUNT(*); reduce versioned dimensions before joining
NUMERATOR AND DENOMINATOREligibility filters constrain the denominator only; NULL-safe booleans
COLUMN VALUES ARE UNKNOWNNames and descriptions are given, values are not — never invent a literal to compare against
CORRECTNESSReal names only; compute per the definition; SAFE_DIVIDE; BigQuery dialect
TENANT SCOPENever blend tenants; resolve any discovered date per tenant, never once globally

Functional surface

The tenant rule is conditional by design

With GAME_ID blank the rule does not simply relax — it flips to requiring GROUP BY org_id, game_id, game_client_id. Either way a result can never silently blend two games. That was the largest correctness hole found in this project: 43 of the 50 tables carry game_id, and early queries filtered on none of them.

06

geoplay/tools.py

The agent's window onto the warehouse. 81 lines.

What it achieves. It supplies the one tool the production agent is allowed to call, invoke_data_agent. In production that tool delegates to a BigQuery-backed SQL agent. Here it returns this project's own metadata instead — the rules, the compact schema, the metric definitions, and the reminder — assembled into a single message.

Where it is used. sql_generation.py passes it to create_agent(tools=[invoke_data_agent]). The simple script does not use it; it loads the same two JSON files itself.

Why it matters architecturally. This is the seam between the local twin and production. Keeping the module path and the tool name identical means the production agent file imports unchanged, so what is exercised here is the real interface rather than an approximation.

FunctionRole
load_json(path)Read one artifact from disk
build_schema_text(columns)Render 948 columns as TABLE x / - col: description lines — about half the tokens of raw JSON
build_metric_text(metrics)Render 49 definitions as name: definition lines
build_context()Both blocks under AVAILABLE TABLES and METRIC DEFINITIONS headers — 109,325 characters
invoke_data_agent(query)The @tool. Returns question + rules + context + reminder, 117,938 characters
Ordering is load-bearing

The reminder is appended last on purpose. Everything before it is buried behind the schema listing, and which rules the model actually followed changed measurably when the reminder moved to the end. This is the only geoplay module that imports langchain_core, which is what keeps the LangChain dependency on the agent side of the line.

07

geoplay/validate.py

Rules are a request. Checks are not. 309 lines, 9 checks, no warehouse required.

What it achieves. It reads the finished SQL as text and reports what the query actually did, independently of what the prompt asked for. This is the half of the system that does not depend on the model complying.

Where it is used. Both generators, at the end of every run. Its findings drive the retry loop: failures are fed back as a correction request, up to MAX_FIX_ATTEMPTS = 2, then the run reports that it gave up rather than pretending.

dialectDATEADD, GETDATE, NVL, TO_CHAR …hard

summed ratiosSUM(arpu_usd) and similarhard
fan-out countCOUNT(*) aliased as a distinct-entity count when the query joins on that entityhard
pruningEXTRACT() or DATE_TRUNC() on a date column inside WHERE or ONhard

Functional surface

Why "review" is not a failure

The pipeline is given column names and descriptions but never values or sample rows, so any literal such as ad_event_type = 'impression' is a guess — and a wrong guess returns zero rows with no error. Those are surfaced for a human to confirm rather than treated as defects; making them hard failures would burn retries trying to fix something that is not broken.

Honest limitation

These are regular expressions over SQL text, not a parser. They catch invalid SQL, not wrong SQL. A COUNT(*) that understated a metric by half, a globally-resolved reference year that silently dropped tenants, and an eligibility filter wrongly applied to a numerator were all found by reading queries, not by a check. Four of the ten rule sections still have no check at all.

08

The scripts

What each entry point is for.

run_pipeline.py — orchestrator

Runs the three stages in order, verifies each produced its artifact, and stops on the first failure with a clear message and exit code 1. Contains no business logic. Launches children with sys.executable so they inherit the same interpreter, and skips stages 1 and 2 when their output already exists — --refresh-dictionary, --refresh-catalogue and --refresh-all force a rebuild.

scripts/data_dictionary.py — stage 1

Reads a BigQuery schema export and asks the model for one business description per column, 20 tables at a time, with response_format={"type": "json_object"} forcing valid JSON back. Writes both JSON and CSV. The expensive stage: three LLM calls for 948 columns. Each row carries a confidence field because the descriptions are model output — currently 848 high, 98 medium, 2 low.

scripts/metric_catalogue_generator.py — stage 2

447 lines, almost all data. The 49 definitions live in the file as a list of tuples and are written straight to JSON. No LLM call, no network, no randomness — running it twice produces a byte-identical file. Its value is that each definition names its numerator and denominator explicitly and distinguishes near-identical metrics: ARPU against ARPPU, Crash Rate against ANR Rate, Tournament Participation against Completion.

scripts/sql_generation_simple.py — stage 3, direct

One chat call. Loads both artifacts, renders them with the shared rules into a system prompt, cleans the reply, validates, retries on failure, prints and saves. Flat module-level functions and two if guards — deliberately readable. Paths anchor to __file__ so it runs from any directory.

scripts/sql_generation.py — stage 3, agent

The production NLToSQLAgent class, unchanged, plus a CLI entry point appended below it. Reaches its context by calling invoke_data_agent through a LangChain agent loop, so it costs two or more calls per question rather than one. Its value is fidelity: what works here can be ported to production as a patch.

Environment trap, from experience

The repo ships a .venv that was created empty — no packages, not even pip, and include-system-site-packages = false. Running the pipeline from inside it fails with ModuleNotFoundError: No module named 'dotenv' even though the system Python has it, because run_pipeline.py correctly propagates sys.executable to its children. Install with uv pip install --python .venv/Scripts/python.exe -r requirements.txt; the venv has no pip, so python -m pip will not work.

Known limits

What this design does not do, stated plainly.

Generated SQL is never executed. No warehouse connection exists in this repo. Table and column names are checked against the data dictionary; semantics are reviewed by reading. A query can pass every check and still be wrong. BigQuery's dryRun flag — which validates and resolves identifiers without executing or charging — is the highest-value unbuilt addition.

Column values are unknown. The dictionary supplies names and descriptions, never values or sample rows. Any literal comparison is a guess, which is why they are surfaced under review rather than trusted.

Four of ten rule sections have no check. APPROACH, CHOOSING THE TABLE, NUMERATOR AND DENOMINATOR and most of OUTPUT SHAPE are enforced by prompt alone. "All checks passed" means "passes the checks that exist".

The tenant check is inert by default. check_game_filter only fires when GAME_ID is set. With it blank, the rule called the largest correctness hole is prompt-enforced only.

Descriptions are model output. Stage 1's 948 descriptions are plausible, not authoritative. The confidence field exists for that reason and the 100 medium and low rows are worth reading by hand.

The metric catalogue is authored here. Its metric_id values were written for this project and may not match the warehouse's own dim_metric.metric_id. Two warehouse queries would settle it, and until they do, resolving ids by name rather than assuming them is the safer path.

No evaluation fixtures. Rule changes are still assessed by generating a few queries and reading them. In practice a change has repeatedly fixed one thing and broken another, and three times a rule change left the validator contradicting it. A fixed list of questions with recorded expectations, re-run on every change, is the missing piece — and the single highest-leverage thing left to build.

Design principle worth carrying forward

Every rule in rules.py exists because a real query got something wrong, and the durable fixes were the ones that paired a rule with a check. Prompt-only rules degrade as the rule set grows and compete with each other for attention; a rule with a deterministic check behind it does not.
