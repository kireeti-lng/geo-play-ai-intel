Project guide · learning reference

Turning a warehouse schema into trustworthy SQL

This project builds two metadata files describing a mobile-games analytics warehouse, then feeds both to a language model so it writes SQL using real column names and computes metrics with the right denominators. This guide walks every Python file: what it does, how it works, and why it is built that way.

repo geo-play-ai-intel python 3.12.4 model openai/gpt-5.2 via OpenRouter scripts 8 files
01

What the project does

The problem it solves, and how you can tell it is working.

A language model asked to write SQL against a warehouse it has never seen will invent table names and guess at metric formulas. Both failures are silent: the query runs, returns a number, and the number is wrong. This project removes both guesses by giving the model two reference documents before it writes anything.

50
warehouse tables described
948
columns with descriptions
49
metric definitions
The core idea

A data dictionary tells the model what exists — which tables and columns are real. A metric catalogue tells the model what things mean — that ARPDAU divides by all daily active users, not just payers. Schema alone cannot carry that second kind of knowledge, which is why the two files are separate artifacts.

Evidence that it works

Asked for ARPDAU by country for the last 7 days, the model produced a per-day aggregate wrapped in an outer AVG() — the arithmetic mean of daily values. That is exactly what the catalogue definition prescribes, and it is not the naive reading a bare schema would suggest. Asked for D7 retention, it excluded cohorts younger than seven days, matching the definition's maturation rule. Neither behaviour was requested in the question; both came from the catalogue.

03

How the data flows

A straight line with two cacheable stages in front of the one that does the work.

Why stage 2 costs nothing

Stage 1 sends 948 column names to a language model in three batches, so it costs money and takes time. Stage 2 makes no model call at all — the 49 definitions are written into the Python file as data. Running it twice produces a byte-identical file. That difference is worth internalising: generation and curation are different jobs, and only one of them needs an LLM.

04

run_pipeline.py — the orchestrator

161 lines. Runs the three stages in order, checks each produced its file, stops on first failure. No business logic of its own.

How it launches the stages

run_pipeline.py · launching a child stage
def run_script(script, extra_args=None):
    command = [sys.executable, script]
    if extra_args:
        command = command + extra_args

    # cwd is the repo root so every stage sees the same relative paths.
    result = subprocess.run(command, cwd=REPO_ROOT)
    return result.returncode == 0

sys.executable is the full path of the Python interpreter currently running. Using it — rather than the string "python" — guarantees the child scripts run under the same interpreter as the pipeline. Launch the pipeline from an activated virtual environment and the stages inherit that environment automatically.

A real failure, and the lesson in it

This project had an empty .venv. Running the pipeline from inside it correctly propagated the venv interpreter to stage 3, which then failed with ModuleNotFoundError: No module named 'dotenv'. The wiring was right; the environment was empty. Fixed with uv pip install --python .venv/Scripts/python.exe -r requirements.txt. When an import fails, ask which interpreter before you doubt the code.

The caching rule

Each metadata stage follows the same pattern: if its output file exists, skip it; a flag forces a rebuild.

FlagEffectWhen you need it
(none)Skip stages 1 and 2 if their files existNormal use
--refresh-dictionaryForce stage 1 to rebuildWarehouse schema changed
--refresh-catalogueForce stage 2 to rebuildYou edited a metric definition
--refresh-allForce bothRebuilding from scratch
Why print needs flush=True

The parent buffers its own output while child processes write straight to the terminal. Without flushing, every stage banner appeared after the output it was meant to label. The say() helper wraps print(text, flush=True) to fix the ordering. A classic subprocess gotcha, well worth remembering.

Guarding each stage

After every stage, check_output() confirms the expected file now exists and exits with status 1 if not. A stage that exits 0 but writes nothing would otherwise be reported as success, and stage 3 would fail later with a confusing error. Failing at the true source of the problem is worth four extra lines.

Stage 1 — data_dictionary.py

138 lines. Reads a BigQuery schema export and asks a model for one business description per column. The expensive stage.

3
LLM calls — 50 tables in batches of 20
948
descriptions produced
2
output formats — JSON and CSV

Step by step

Load config. load_dotenv() runs first, so the CSV path can come from BQ_EXPORT_CSV in .env, falling back to a hardcoded default.
Guard the input. If the CSV is missing, print a clear message and sys.exit(1) instead of raising a traceback.
Read and group. csv.DictReader walks the rows; defaultdict(set) groups columns under their table and drops duplicates in one step.
Sort. Tables and columns are sorted so batching is deterministic and reruns are comparable.
Batch. chunk_dict() yields 20 tables at a time, keeping each prompt small enough to stay reliable.
Ask the model with response_format={"type": "json_object"}, which forces valid JSON back.
Write both outputs — JSON for machines, CSV for reading in a spreadsheet.

The grouping trick, unpacked

scripts/data_dictionary.py · grouping
table_groups = defaultdict(set)
with open(CSV_PATH, newline="", encoding="utf-8-sig") as f:
    for row in csv.DictReader(f):
        table = row["table_name"].strip()
        column = row["column_name"].strip()
        if table and column:
            table_groups[table].add(column)

Three things happen at once here. defaultdict(set) means you never check whether a key exists before adding to it. Using a set rather than a list makes duplicate columns disappear for free. And encoding="utf-8-sig" strips the byte-order mark that Excel and BigQuery exports often put at the start of a CSV — without it the first column name arrives with invisible junk attached.

Where this stage is fragile

Descriptions are model output, so they are plausible rather than authoritative. Each row carries a confidence field for that reason. In the current file: 848 high, 98 medium, 2 low. The low and medium rows are the ones worth reading by hand.

Stage 2 — metric_catalogue_generator.py

447 lines, almost all of it data rather than logic. No model call, no network, no randomness.

scripts/metric_catalogue_generator.py
# (metric_id, metric_name, definition)
METRICS = [
    (
        "ad_arpdau",
        "Ad ARPDAU",
        "Ad ARPDAU is the quotient of gross advertising revenue "
        "recognized on a given day and the count of daily active "
        "users on that same day...",
    ),
    # ... 48 more
]

metrics = [
    {"metric_id": metric_id, "metric_name": metric_name, "definition": definition}
    for metric_id, metric_name, definition in METRICS
]

Two Python details worth noticing

Implicit string concatenation. Adjacent string literals with no operator between them are joined by Python at parse time. That is how a long definition wraps across several lines without + signs or backslashes.

Tuple unpacking in a comprehension. The for metric_id, metric_name, definition in METRICS line pulls all three values out of each tuple in one move, which is why the dictionary above it reads so plainly.

Why the IDs are typed by hand

It would be tempting to derive metric_id from metric_name automatically. Four names break a naive slug function: Ad eCPM (USD), Stickiness (DAU/MAU), Transactions / Paying User, Total Revenue (IAP+Ad). Writing the IDs out keeps the script simple and the IDs stable. Simple beats clever when the input set is small and fixed.

What makes the definitions useful

Every definition names its numerator and denominator explicitly, and near-identical metrics are deliberately distinguished rather than left vague:

PairWhat separates them
ARPU vs ARPPUAll active users vs payers only in the denominator
Ad ARPU vs Ad ARPDAUPeriod-unique users vs per-day normalisation
Crash Rate vs ANR RateProcess termination vs main-thread hang; never summed
Tutorial Completion vs FTUE Drop-offTutorial starters vs the wider onboarding path
Tournament Participation vs CompletionEligible users vs entrants as the denominator

This is the part that makes stage 3 accurate. A schema listing can say revenue_iap_usd exists; only a definition can say which users belong in the denominator when you divide by it.

Edit the script, not the JSON

The JSON file is generated output. Editing it directly works until the next run of stage 2 overwrites your change. Edit METRICS in the script, then run with --refresh-catalogue — without that flag the stage skips and your edit never reaches the JSON.

243 lines. Loads both metadata files, renders them into a prompt, asks for one query, prints and saves it. The file that does the actual job.

The context budget

Sending raw JSON would cost roughly 57,000 tokens per question. Rendering it as compact lines roughly halves that:

BlockCharactersApprox. tokens
Schema — 50 tables, 948 columns88,914~22,200
Metrics — 49 definitions20,324~5,100
Combined109,238~27,300

Everything is sent every time, with no filtering by keyword. That is a deliberate trade: keyword filtering would be cheaper, but a missed keyword would silently starve the model of the one table it needed — a hard failure to debug. Predictability was chosen over cost.

The prompt rules

system prompt · the rules block
Rules:
- Use only the tables and columns listed under AVAILABLE TABLES. Do not invent names.
- If the question names a metric from METRIC DEFINITIONS, compute it exactly as the
  definition states, using the numerator and denominator it specifies.
- Return only the SQL query. No explanation, no markdown, no code fences.

The second rule is the load-bearing one. It is what turns the catalogue from decoration into behaviour.

Paths anchored to the file, not the folder

scripts/sql_generation_simple.py · path resolution
REPO_ROOT = os.path.dirname(os.path.dirname(os.path.abspath(__file__)))
METRIC_PATH = os.path.join(REPO_ROOT, "metric_catalogue", "metric_catalogue.json")

Read it inside out: __file__ is this script's path, abspath makes it absolute, and two dirname calls climb from the file to scripts/ to the repo root. The result is that the script finds its data no matter which folder you run it from. A plain relative path such as "output/data_dictionary.json" would only work when the current folder happened to be the repo root.

Naming the saved file

make_slug() lowercases the question, replaces every non-alphanumeric character with a space, drops filler words from a STOP_WORDS set, and keeps the first eight words:

QuestionFilename slug
What is ARPU for the last 30 days?arpu_last_30_days
How many sessions per DAU did we have yesterday?sessions_dau_yesterday
What is the Ad eCPM (USD) trend?ad_ecpm_usd_trend
Transactions / Paying User last weektransactions_paying_user_last_week
(empty or all filler)query

Stripping to alphanumerics also removes characters Windows forbids in filenames, so the slash in Transactions / Paying User causes no trouble. A timestamp is appended so re-asking the same question never overwrites the earlier answer.

08

Supporting scripts

Three files the pipeline never calls, each useful for a different reason.

scripts/json_schema_generator.py

42 lines, no LLM. Reads the same BigQuery CSV and writes payload_source/schema.json — 50 tables with each column's data type. Where the data dictionary answers what does this column mean, this answers what type is it. Stage 3 does not currently use it, but type information is what you would add to stop the model comparing a string to a date.

scripts/main.py

69 lines. A smoke test: sends one tiny prompt and prints the reply plus token counts. Run it first whenever something breaks, to separate my key or model is wrong from my pipeline is wrong. It is how the model change to openai/gpt-5.2 was confirmed working.

python scripts/main.py · expected output
model:  openai/gpt-5.2
reply:  connection ok
tokens: 12 in / 16 out

test.py

125 lines. A scaled-down twin of stage 1 that uses four made-up tables defined inline instead of the real CSV, and prints results instead of writing files. Useful for learning the batching pattern without spending tokens on 948 columns. Its BATCH_SIZE is 2 so you can watch the loop actually loop.

sql_generation.py — the reference copy

133 lines, and the most misleading file in the repo. Read it to understand production; do not expect it to run.

It is a copy of src/geoplay/agents/nl_to_sql_agent.py from a separate production repository.

sql_generation_simple.pysql_generation.py

It was simplified in place — type annotations removed, static methods lifted to module functions, a bare except Exception narrowed to json.JSONDecodeError — while keeping its public surface and its system prompt character-identical. 57 differential checks against the original confirmed identical behaviour.

A bug deliberately preserved

When the agent returns a message with empty content, the response extractor falls through and stringifies the whole result dictionary, so the intended ValueError never fires and garbage is returned as SQL. This exists in the original and was left alone, because the goal was behaviour-preserving simplification. Knowing the difference between fixing and refactoring matters: doing both at once makes it impossible to tell which change caused a new failure.

The shape every script here shares

Constants at the top, functions in the middle, a flat run of statements at the bottom. No classes unless something genuinely needs state. You can read any file top to bottom and know what happens, in order — which is exactly why they are easy to debug.

First-time setup

Install dependencies into the virtual environment: uv pip install --python .venv/Scripts/python.exe -r requirements.txt

Everyday use

PowerShell · from the repo root
# normal run: stages 1 and 2 skipped, only stage 3 runs
python run_pipeline.py "What is ARPU for the last 30 days?"

# after editing a metric definition
python run_pipeline.py --refresh-catalogue "What is ARPU for the last 30 days?"

# skip the runner, go straight to SQL generation
python scripts/sql_generation_simple.py "What is ARPU for the last 30 days?"
Name the metric in your question

"Total revenue generated per user" describes ARPU but does not name it, and it is ambiguous between ARPU and ARPPU — two real metrics with different denominators. Saying ARPU outright gets the catalogue definition applied and produces a tighter filename.

Two known limitations

Generated SQL is never executed. No warehouse connection exists in this project, so a query can be syntactically valid and still be wrong. Read it before you trust it.

The dialect is assumed. SQL_DIALECT is set to BigQuery because the source CSV is a BigQuery export. If the warehouse is something else, change that one constant.
