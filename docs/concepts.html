Revision notes · Built while learning, version by version

Every concept behind a 60-line AI script.

One small Python file asks a question to an AI model and prints the answer. Underneath it sit about thirty ideas worth knowing — secrets handling, API gateways, message roles, tokens, cost. This is the map of those ideas, in the order they were added.

01

The whole thing in one sentence

Before the details, hold this shape in your head. Everything else is a refinement of it.

Your script sends a question over the internet to a company that owns a big AI model, and prints back what the model says. That's it. The script does not contain any intelligence itself — it is a messenger. Once you accept that, the concepts sort themselves into four natural questions:

Who am I?

Proving you're allowed to ask. This is the API key, and everything about keeping it secret.

Where do I send it?

An address on the internet, and which model at that address should answer.

What exactly do I say?

The shape of the request — a list of messages, each with a role.

What does it cost?

Tokens, prices per million, and the limits you set to stay cheap.

03

Version 1 — get one real answer back

The goal of a first version is never elegance. It is proof that the pipe works end to end.

Why a secret can't live in the code

An API key is a password that spends real money. If it sits inside main.py, then the key travels wherever the file travels — into git history, into a screenshot, into a shared folder. Git history is the dangerous one: deleting the line later doesn't remove it, because git remembers every past version.

So we split the project in two: code that is safe to share, and secrets that never leave your machine. The code refers to the secret by name and looks it up at run time.

Principle

Code says "give me the value called OPENROUTER_API_KEY". It never says what that value is. Anyone can read your code; only your machine knows the answer.

What python-dotenv is actually for

An environment variable is a named value the operating system holds for running programs. It's the standard place for secrets, because it belongs to the machine rather than the project. The catch: setting one by hand in the terminal only lasts for that terminal session, so you'd retype it constantly.

python-dotenv closes that gap. It reads a plain text file named .env and loads each line into the environment when the script starts. You write your key once, in a file git is told to ignore, and every future run picks it up automatically.

What this buys us: the convenience of hardcoding, with none of the exposure. And when this project eventually runs somewhere else — a server, a scheduled job — that environment supplies the variable its own way and the code doesn't change at all. That portability is the real payoff.

The trick that makes this work with OpenRouter

We install the openai library but we are not talking to OpenAI. This surprises people, and it's worth understanding because it's a genuinely important industry pattern.

OpenAI published the shape of their API — which address to POST to, what JSON to send, what comes back. That shape became a de-facto standard, and other services deliberately copy it. OpenRouter is one of them. So the OpenAI client library works against OpenRouter with a single change: we hand it a different base_url.

Why it matters to us: one library and one mental model gets us access to hundreds of models from many vendors. And if we ever switch gateways, the change is one line, not a rewrite.

Why a gateway instead of going direct

Going direct to each vendor

A separate account, key, bill and client library for every company. Comparing two models means writing two integrations.

Going through OpenRouter

One account, one key, one bill, one library. Swapping model — even across vendors — is editing a single string. That is exactly what we did in V4.

For someone learning, the ability to try a model without a new signup is worth a great deal. We confirmed 414 models available through the one key.

The request shape: roles, not just text

You might expect to send a single string. Instead you send a list of messages, and each message carries a role. This is the one piece of structure worth memorising, because everything about prompting builds on it.

the shape of every request — worth knowing by heart
# a list, in order, of who said what
[
  { "role": "system", "content": "standing instructions" },
  { "role": "user",   "content": "the actual question" }
]

There are three roles you'll meet. system sets behaviour and identity. user is you. assistant is what the model previously said — you only include it when you want the model to remember earlier turns, which is the whole basis of multi-turn chat.

Why a list and not a string: because the model has no memory. Every request must carry the entire conversation you want considered. The list is the memory, and you own it.

What V1 also had, and later lost

The first version wrapped everything in error handling — five separate branches catching bad keys, missing models, rate limits and network failures — and organised the code into functions with a command-line flag parser. All of that is normal in production code, and all of it was removed in V2. The reasoning is in the next section, and it's a genuine lesson rather than a reversal.

Why removing error handling helps a learner

Error handling replaces an ugly, detailed failure with a tidy, vague one. That is a good trade for a user of finished software, and a bad trade for someone learning — because the ugly detail is the lesson.

Compare the two. With handling, a bad key printed "OpenRouter rejected the API key." Clean, but it teaches nothing. Without handling, Python prints a traceback ending in openai.AuthenticationError: Error code: 401. Now you've met a real exception type and a real HTTP status code, and you can search for either.

What we achieve by removing it: the code becomes the logic and nothing else. Every remaining line does visible work.

Balance

This is a learning choice, not a universal rule. Software other people depend on needs error handling — a scheduled job shouldn't die on one network blip. The skill is knowing which situation you're in. Add handling when a failure needs a response, not merely a report.

How to read a traceback

A traceback looks intimidating because it's printed in the wrong order for humans. It starts at the outermost call and works inward. Read the last line first — that's the actual error and it usually names the problem exactly, as in KeyError: 'OPENROUTER_API_KEY'. Then look upward for the line number in your file, ignoring the frames inside libraries.

Plain if/else over clever one-liners

Python lets you choose a value in one line, and V1 did. V2 spends four lines on the same decision using ordinary if and else. It's longer and better here: the four-line version reads in the order it happens, and there's no new syntax between you and the idea. Compact forms are worth learning later, once the underlying decision is obvious to you.

05

Version 3 — make it easy to ask anything

Turning a fixed connection test into a tool you can actually put questions to.

A marked place to type

V2 had its question buried in the middle of the file, tangled up with the sending logic. If you're going to edit something daily, it should be at the top, clearly labelled, and separated from machinery you shouldn't touch. That's the entire reasoning behind the PROMPT block — it isn't a programming technique, it's respect for the person editing the file.

It uses triple quotes so your question can span several lines, and .strip() when sending so the surrounding blank lines you naturally leave don't get transmitted as part of the question.

Two ways in, and which wins

You can edit PROMPT, or pass a question on the command line. The command line wins when both exist. That ordering is deliberate: the file holds the thing you ask often, and the command line handles the one-off you don't want to save. Deciding which input takes priority is called precedence, and any tool with more than one input source has to answer it.

The system prompt, and why it's separate

SYSTEM_PROMPT is for instructions that should apply to every question — a persona, a format, a language, a standing constraint. It's kept apart from the question because it has a different lifetime: your question changes constantly, your standing instructions rarely.

We verified it works by setting it to "answer only in French" and asking an English question — the reply came back in French. That is the fastest way to convince yourself a system prompt is really reaching the model.

What it achieves for this project: when this becomes a data-intelligence tool, the system prompt is where "you are a games analytics assistant, answer with metrics and be concise" will live — written once, applied to every query.

06

Version 4 — choosing a model, and paying for it

The version where the concepts stop being about Python and start being about economics.

Tokens — the unit of everything

Models don't read letters or words. They read tokens: chunks of text, roughly ¾ of a word each on average, so 100 tokens is about 75 English words. Common words are usually one token; unusual words, names and code split into several.

Tokens matter because they are simultaneously the unit of cost, the unit of limits, and the unit of speed. Understand tokens and pricing, context windows and truncation all become obvious at once.

Input and output are counted and priced separately, and output is usually far more expensive — output for our model costs six times its input. Our real measurement: an analytics question used 27 input and 70 output tokens.

Reading a price, and what our swap actually did

Prices are quoted per million tokens, which is why they look reassuringly small. Here is the comparison that decided V4, with live figures pulled from OpenRouter:

The useful lesson: newer is not automatically dearer. The model we moved to is a generation ahead, costs less per input token than the one it replaced, and holds eight times as much text. Checking current prices beat assuming.

The same table shows the other half of the lesson. One family can span a 50× price range — the biggest sibling costs fifty times the smallest on input. "Which model" is a cost decision as much as a quality one, and for learning, the cheap end is almost always right.

Context window — the size of the desk

The context window is the maximum tokens a model can consider at once: your system prompt, your question, the conversation history you chose to include, and the reply it's composing, all together. Exceed it and the request is rejected or the oldest material gets dropped.

Ours is 1,050,000 tokens — several long books' worth. That's far more than a single question needs, but it becomes the thing that matters the moment you start attaching data or keeping conversation history.

max_tokens — a spending limit you set

max_tokens caps how long the reply may be. It is not a suggestion to the model about style; it's a hard ceiling where generation stops, mid-sentence if necessary. We set 500.

Why bother, given how cheap this is: because it's a safety rail with no downside at our scale. A prompt that accidentally invites an enormous answer can't quietly run up a bill or a long wait. If a reply ever gets cut off mid-sentence, that's the cap doing its job and telling you to raise it.

Watching the meter

Every response includes a usage report, and we print it. Making cost visible on every single run is how a sense of scale gets built — after a few dozen runs you'll know roughly what a question costs without calculating. For the record: that 27-in / 70-out analytics question cost about $0.000045, or roughly 22,000 questions per dollar.

AVOID

OpenRouter also offers "always latest" aliases that auto-follow a vendor's newest release. Tempting, but we deliberately didn't use one: it currently resolves to the $5.00 / $30.00 tier — fifty times our input cost — and its price and behaviour can change without you editing a thing. Pin an explicit model; upgrade when you decide.

07

The three ideas worth re-reading

If you forget everything else here, these are the ones that keep paying off.

1 · The model has no memory

Each request is judged entirely on what you send in it. The model isn't holding your previous question somewhere; there is no session. Chat products feel continuous because they resend the whole prior conversation every single turn.

Consequences worth remembering: conversation history is your job, longer conversations cost more (you're resending everything), and this is why the request takes a list of messages.

2 · Copied API shapes are leverage

One popular API shape being copied by competitors means one library, one mental model, and hundreds of interchangeable models. Our whole vendor switch was a base_url and a model string.

Look for this pattern elsewhere — S3-compatible storage and Postgres-compatible databases work the same way, and recognising it saves you learning the same thing twice.

3 · Secrets are a boundary, not a habit

Three small files enforce one rule between them: .env holds the secret, .gitignore stops it being committed, .env.example documents what's needed without revealing it.

The example file is the underrated one — it's how the next person (or future you) knows which variables to set without anyone having to share a live key.

Bonus · Verify, don't assume

Model names and prices change constantly. Every figure in this document came from asking OpenRouter's live model list, not from memory — and doing that caught a default model that would have been wrong.

Any list of available models is a fact about today. Re-check it rather than trusting a document, this one included.
